# 09：MSQ 區塊的內部 —— 地圖層

日期：2026-08-13（§1–§2 於 2026-08-14 依 `docs/re/16` 改寫）
輸入：解密後的 42 個 MSQ 區塊（`docs/re/08`）

## 1. 地圖：已確認

每個 MSQ 區塊解密後**從位移 0 開始是地圖**，一個 byte 兩格（4 bits 一格、16 種地形）。

地圖區的長度不是固定的，由執行檔內的選擇表決定（`sub_1841F`，見 `docs/re/16` §1）：

| 地圖區長度 | 格數 | 尺寸 | 區塊數 |
|---|---:|---|---:|
| `0x600`（1,536） | 3,072 | 64 × 48 | 38 |
| `0x1800`（6,144） | 12,288 | 128 × 96 | 4 |

驗證用空間自相關：把地圖區展成 nibble 陣列，統計「相鄰格相同」的比例。
隨機資料的期望值是 1/16 ＝ 0.0625。

| 區塊 | 水平自相關 | 垂直自相關 |
|---|---:|---:|
| 42 個區塊的範圍 | 0.393 – 0.875 | 0.529 – 0.837 |
| 最低（`game1` #28） | 0.393 | 0.674 |
| 最高（`game1` #26） | 0.875 | 0.831 |

**42 個區塊全部落在 0.39 以上，兩個方向都是**——比隨機高了 6–14 倍。
地形資料才會有這種空間連續性；如果切點錯了或解密錯了，不會出現這個結果。

以列寬掃描找極值時，38 個小區塊裡有 32 個在 64 nibble 列寬最高、
4 個大區塊在 128 nibble 列寬最高，剩下 6 個小區塊在 32 列寬最高（可能是地形單純
造成的假峰，未定案）。

用滿全部 16 種 nibble 值是常態（38/42 個區塊如此），少數只用 6–9 種
（`game1` #0 用 9 種、#26 用 7 種，`game2` #12 用 6 種、#22 用 8 種），
那些多半是地形單純的區域。

## 2. 地圖之後：記錄區

地圖區之後接的是記錄區標頭（0x5C bytes）與各 section。
完整佈局、section 位移表、兩層索引與驗證結果見 **[`docs/re/16`](16-msq-block-layout.md)**。

## 3. 名稱字串是明文

同一個區塊的 `+0x9CD` 起是一串 NUL 分隔的明文 ASCII：

```
Titanium  Clawer  Vanadium  Vulture  Chopter  Steel  Reaver
Silicon   Sniper  Silver    Strangler  Robot …
```

原版的怪物名是「形容詞 ＋ 名詞」組出來的（`Titanium Clawer`、`Silicon Sniper`），
所以字串表裡兩類詞分開存放。

**解密之後就是明文，沒有第二層編碼**——至少名稱這一類如此。
這對中文化是好消息：這批字串可以直接處理。

至於劇情敘述文字，目前**在 MSQ 區塊裡沒有找到**。
42 個區塊中只有 4 個含 50 個以上的英文單字，而那幾個看起來都是名稱表。
敘述文字可能在 `ALLHTDS1`／`ALLHTDS2`（尚未分析）或目錄裡那 8 個沒有 MSQ 區塊的資源編號。
**這是待查方向，不是結論。**

## 4. 順帶解出：存檔是兩份輪替

`sub_18744`（189 bytes）不是地圖載入器，是**存檔載入**：

```asm
0x18745  mov  byte ptr ds:9168h, 80h    ; 指向 GAME1
0x1874C  call sub_11445
0x1874F  mov  dx, 53C5h                 ; seek 到 GAME1 的 0x53C5
0x1876B  call sub_11AA3                 ; 讀 0x800 bytes → ds:7131h
0x18776  call sub_115E5                 ; 讀 0xA00 bytes → ds:C062h
0x1877D  mov  byte ptr ds:9168h, 40h    ; 換成 GAME2
0x18787  mov  dx, 8BC7h                 ; seek 到 GAME2 的 0x8BC7
0x187A1  call sub_11AA3                 ; 讀 0x800 bytes → ds:2700h
0x187AC  call sub_115E5                 ; 讀 0xA00 bytes → ds:0
; ── 比較兩份的 32-bit 序號，較新的留下 ──
0x187B2  mov  dx, ds:7226h
0x187B6  mov  cx, ds:7228h
0x187C5  sub  dx, [bx]
0x187C9  sbb  cx, [bx]                  ; 32-bit 比較
0x187CB  jnb  short loc_187E7
0x187D4  rep movsb                      ; 第二份較新 → 覆蓋過去
```

| 項目 | 值 |
|---|---|
| 存檔位置 | `GAME1` 的 `0x53C5`、`GAME2` 的 `0x8BC7`（在 MSQ 區塊內部的固定位移） |
| 每份大小 | `0x800`（2,048）＋ `0xA00`（2,560）兩段 |
| 版本判定 | `ds:7226h`／`ds:7228h` 的 32-bit 序號，大的較新 |
| 載入後 | 兩段分別放在 `ds:7131h` 與 `ds:C062h` |

**兩份輪替寫入**是磁片時代的防斷電做法：寫壞一份還有另一份。
重製版要不要照做是設計問題，但存檔格式必須照這個結構讀。

## 5. 新工具

`tools/ida/export_range_refs.py`：掃全部指令，找出運算元數值落在指定範圍的引用。
知道「結構在 `ds:X`」之後反問「誰在碰它」時用。
內建 `& 0xFFFF`，避免 16-bit 符號擴展造成的零命中（`docs/re/03` §7）。

```sh
WL_IDA_TARGET=… tools/ida.sh run tools/ida/export_range_refs.py <out.json> 0x800 0x8C0
```

⚠ 這次的教訓：**零命中要先想「存取方式是不是不同」**。
`ds:0x800` 只有四筆命中，不是因為沒人用地圖後面的資料，
而是因為那些欄位透過基址暫存器存取，數值根本不會出現在運算元裡。
