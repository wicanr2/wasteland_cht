## 1. 把缺口變成數字

`TestScriptOpcodeCoverage` 掃 42 張地圖的 section 6 腳本記錄，
對每一筆查出 opcode（走 section `0x10`），試跑一次，記下
`Handled ＝ false` 的那些，並統計**有幾格指到它**。

`Handled ＝ false` 是啞掉的缺口：遊戲照跑、測試全綠，代價是那一格什麼都不發生。
`docs/re/75` §8 說「fallback 要能被統計」——這一份就是那個統計。

## 2. 結果

| 階段 | 未實作的 opcode | 記錄數 | **有格子指到的格數** |
|---|---:|---:|---:|
| 盤點當下 | 23 種 | 148 | **37** |
| 實作 op 26 之後 | 22 | 113 | 7 |

## 3. 四個非法 opcode

盤點順帶抓到四筆記錄的 `+0x00` 查出來是 1282／2271／26478／29813——
遠超過 44。那是 section `0x10` 的索引越界（陣列長度不能用 `SectionCount` 算，
`docs/re/71` §5.2），讀到的是記錄本體的資料。

`Step()` 已經擋住（`op < 0 || op >= OpCount` → `Handled ＝ false`），
四筆都是 0 格，所以不影響。列在這裡是因為**它們是「這一筆記錄根本不是腳本」
的訊號**——如果哪天有格子指到其中一筆，那代表別處的解讀錯了。

## 4. 門檻寫進測試

```go
if missCells != 0 {
    t.Errorf("有格子指到的 opcode 還有 %d 格沒實作", missCells)
}
if missRecords > 85 {
    t.Errorf("未實作的 opcode 記錄數 %d 超過門檻 85", missRecords)
}
```

格數是**硬門檻**（玩家踩得到的一格都不能漏），記錄數是遞減的軟門檻——
實作了新的 opcode 就把數字調小，回退會紅。

## 6. 這一輪學到的（寫成規則）

- **接上一個子系統之後，先量它的覆蓋率再往下做。** 直譯器接上的當下看起來
  「能跑」，實際上 37 格會靜靜地什麼都不發生。**量一次就知道要補哪幾個**，
  而且補完有數字證明。
- **把「還沒做」與「這次不適用」分開回報。** `Handled ＝ false` 這個欄位
  早就設計好了，但沒有人統計它——**設計了訊號卻不讀，等於沒有訊號。**
- **軟門檻比清單好維護。** 「未實作記錄數 ≤ 85」會隨著實作往下走，
  而一份手寫的「還沒做的 opcode 清單」會過期。
