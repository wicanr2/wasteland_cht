## 1. 問題

選單文字裡的 `\x10` 一直只知道「捕捉下一個字元」（`docs/re/14` §4.1，
處理程式在 `0x19EB8`，兩條指令 `mov byte ptr ds:4703h, 1` ＋ `retn`）。
捕捉去哪、誰讀、讀了做什麼，一直沒追。

這件事決定中文化能不能把 `\x10Yes` 翻成 `\x10是`——
如果被捕捉的字元會回頭當成按鍵用，那 Big5 的首位元組就會被當成鍵送出去。

## 2. 捕捉寫進「每一列的熱鍵表」

`\x10` 只是把旗標 `ds:4703h` 設起來。真正寫入在文字輸出的組行版
（`sub_19DC3`）與直繪版（`sub_19E53`）各一份，形狀相同：

```
0x19DCB  8a160347   mov  dl, ds:4703h        ; 旗標
0x19DCF  84d2       test dl, dl
0x19DD1  7410       jz   short loc_19DE3
0x19DD3  8a1e7346   mov  bl, ds:4673h        ; 目前列號（1 起算）
0x19DD7  80eb01     sub  bl, 1
0x19DDA  8887dc8d   mov  [bx-7224h], al      ; ds:8DDCh[列−1] ← 這個字元
0x19DDE  c606034700 mov  byte ptr ds:4703h, 0
```

`[bx−0x7224]` 的基底就是 `ds:8DDCh`——同一塊被控制碼 `\x11` 清成零：

```
0x19EBE  bedc8d     mov  si, 8DDCh
0x19EC1  b91900     mov  cx, 19h             ; 25 bytes
0x19EC6  8804       mov  [si], al            ; al ＝ 0
```

**所以 `ds:8DDCh` 是「文字視窗每一列各記一個字元」的表**，25 列份。
`\x11` 清表、`\x10` 記一格。文字視窗捲動時這張表跟著捲
（`sub_1A0C5` 的 `0x1A11C`：`si ← 8DDCh`，逐 byte 前移一格、尾巴補 0），
所以列號與畫面永遠對得上。

推論等級：**已確認**。

## 3. 讀的人是滑鼠

`sub_18860` 是滑鼠的**熱區派工**：`ds:0CAEBh` 起，每筆 10 bytes
＝ `x1, y1, x2, y2, handler`，游標落在矩形內就 `call ax`（`0x188D0`）。

21 筆熱區（`tools/dump_word_table.py`，座標為十進位）：

| # | x | y | handler | 身分 |
|---:|---|---|---|---|
| 0 | 0–311 | 104–175 | `0x18C2E` | **隊伍名單**：列 ← `(y−0x7D)>>3 ＋ 1`，上限 `ds:4653h`（隊伍人數），送出 `'0'＋列` |
| 1 | 8–280 | 8–120 | `0x18C62` | **地圖視窗**：依游標落在哪一個三角象限查 `ds:C05Dh` 送方向鍵；中央小框送 ESC |
| 2 | 104–295 | 5–100 | `0x18CE7` | **訊息視窗**：見下 |
| 3 | 0–319 | 189–196 | `0x18D16` | 底列，送 `0x0D` |
| 4–20 | 各處小按鈕 | | `0x18BFF` | 固定鍵，值取自第二張表 `ds:0CBBDh`（每筆 6 bytes，鍵在 `+0x03`） |

訊息視窗那一支：

```
0x18CED  8b16fb7d   mov  dx, ds:7DFBh        ; 滑鼠 Y（int 33h AX=3 的 DX）
0x18CF1  83ea05     sub  dx, 5               ; 減視窗上緣
0x18CF4  d1ea×3     shr  dx, 1  (三次)       ; ÷8 ＝ 字高
0x18CFA  8bf2       mov  si, dx
0x18CFC  8a84dc8d   mov  al, [si-7224h]      ; ds:8DDCh[列]
0x18D00  84c0       test al, al
0x18D02  7410       jz   short loc_18D14     ; 那一列沒登記熱鍵 → 不算按鍵
0x18D0A  f706f77d0010 test word ptr ds:7DF7h, 1000h   ; 按鍵狀態
0x18D12  f9         stc                      ; CF ＝ 1 ＋ al ＝ 那個字元
```

而 `sub_18EFE`（真正的取鍵）**先問滑鼠再問鍵盤**：

```
0x18F38  e825f9     call sub_18860
0x18F3B  7217       jb   short loc_18F54     ; 滑鼠給了字元 → 直接當按鍵用
0x18F3D  b401 cd16  int  16h                 ; 否則才讀鍵盤
```

**整條鏈閉合**：`\x10X` 讓「點這一列」等同於「按 X 鍵」。

推論等級：**已確認**（每一段都讀到程式碼；熱區表 2 的 handler 值 `0x8CE7`
與 `y1 ＝ 5` 同時對上 `0x18CE7` 的 `sub dx, 5`，兩邊是獨立來源）。

## 4. 鍵盤那條路完全不看這張表

`ds:8DDCh` 的唯一讀者是 `0x18CFC`。鍵盤按下去的字元走各自的比對：

| 比對方式 | 位址 | 用在 |
|---|---|---|
| **寫死的字母** | `sub_12619`：`cmp al,'N'` → 失敗；`cmp al,0x1Bh`（ESC）→ 失敗；`cmp al,'Y'` → 成功 | 全部的是／否詢問 |
| **靜態字母表**：等一個鍵，在 `ds:4680h` 指的 NUL 結尾字串裡找位置，回傳索引 | `sub_173B0` | 戰鬥指令（表 `ds:A44Dh` ＝ `" HAWRELU"`，`docs/re/38` §2）、隊伍選單 |
| **只收數字** | `sub_1721B`：只收 `'1'`–`'9'`，`and al,0Fh` 後須 ≤ 選項數 | 地圖 nibble 8 的多選一（`docs/re/29` §3） |

是／否那條路的完整形狀（地圖 nibble 10、記錄 `+0x00` bit7 設起來時）：

```
0x16AEA  e82a00     call sub_16B17     ; 印區塊字串 記錄[+0x00] & 0x3F
0x16AF0  b067       mov  al, 67h
0x16AF2  e8bd01     call sub_16CB2     ; 印 exe 字串表 1 的第 0x67 條
0x16AF5  e821bb     call sub_12619     ; 等 Y／N／ESC
```

`exe:1:103`（＝ 表 1 第 `0x67` 條）就是
`\rEnter new location?\r\r\x11\x10Yes\r\x10No\r`——
**畫面上印 `Yes`／`No`，比對的是寫死的 `'Y'`／`'N'`**。
兩者一致純粹因為英文原文的字首剛好就是那個鍵。

推論等級：**已確認**。

## 5. 對中文化的硬約束

`\x10` 後面那個字元有兩個身分：**畫面上的第一個字** ＝ **點擊那一列送出的鍵**。
翻成中文之後：

- 滑鼠：`\x10是` 會把 Big5 `是` 的首位元組 `0xAC` 當成按鍵送出去，
  而 `0xAC` 不對應任何比對條件——點擊直接失效。
- 鍵盤：比對照樣是 `'Y'`，但畫面上沒有任何字告訴玩家要按 Y。

兩邊都壞，而且**壞法不一樣**：滑鼠是點了沒反應，鍵盤是玩家不知道按什麼。

**規則：`\x10` 後面必須原樣保留原文的那個 ASCII 字元，中文接在它後面。**

```
原文    \x11\x10Yes\x0D\x10No\x0D
中文    \x11\x10Y 是\x0D\x10N 否\x0D
```

這與 `docs/re/40` §4 對戰鬥選單下的結論是同一條規則的兩個實例
（那裡是 `\x10R 逃跑`），差別只在戰鬥選單的鍵來自靜態字母表、
訊息視窗的鍵來自寫死字母或區塊答案字串——**不論哪一種，鍵都不跟著翻譯走**。

規格與編譯期的檢查寫在 [`docs/spec/11`](../spec/11-translation-catalogue.md) §5。

## 6. 順帶確認到的

- **`ds:7DF9h`／`ds:7DFBh` 是滑鼠座標**，`ds:7DF7h` 是按鍵狀態位元，
  三個都由 `sub_18928` 經 `int 33h` AX=3 更新（`ds:8DDBh` ＝ 0 時不呼叫，
  即「沒有滑鼠驅動程式」的路徑，走 `nullsub_2`）。
- **訊息視窗的可用列數是 12**（y 5–100，每列 8 px），
  熱鍵表卻是 25 格——表比視窗大，所以捲動時不需要邊界特判。
- `ds:4673h` 是**目前列號、1 起算**，這也是 `\x10` 要先減 1 的原因。

## 6. 按鍵巨集：F1–F10 播放、Alt+F1–Alt+F10 錄製

`sub_18EFE`（鍵盤讀取本體）裡有一整套錄放機制，跟在讀鍵之前：

| 變數 | 意思 |
|---|---|
| `ds:0C062h` | 巨集緩衝區，**10 個 × 256 bytes** |
| `ds:0CA62h` | 目前在緩衝區裡的位置 |
| `ds:0CA63h` | 正在錄第幾個（1–10；0 ＝ 沒在錄） |
| `ds:0CA64h` | 正在播第幾個（1–10；0 ＝ 沒在播） |

邊界自己對得起來：`0xC062 + 10 × 256 ＝ 0xCA62`，三個狀態變數就緊接在
緩衝區後面——**這是「10 × 256」這個佈局的證據，不是從程式碼裡數出來的猜測**。

```
0x18F0C  ds:CA64h 非 0 → 從緩衝區取下一個字元；取到 0 就把 CA64h 清成 0（播完）
0x18F3D  否則 int 16h 讀鍵；al ＝ 0 的擴充鍵轉成 ah | 0x80
0x18F56  al ∈ [0xBB, 0xC4]（F1–F10）→ 正在錄就丟掉，否則 CA64h ← al − 0xBA、位置歸零
0x18F6F  al ∈ [0xDE, 0xE7]（Alt+F1–Alt+F10）→
             沒在錄  → CA63h ← al − 0xDD、位置歸零（開始錄）
             同一個  → 寫一個 0 收尾、CA63h ← 0（結束錄）
0x18FAE  正在錄而且這一個字元非 0 → 寫進緩衝區（位置到 0xFF 就不再寫）
0x18FF0  最後才把 'a'–'z' 轉成大寫（§2.1 of docs/re/46）
```

⚠ **順序值得注意**：巨集在**轉大寫之前**錄、播出來的字元也**會再經過轉大寫**，
所以錄的是原始鍵碼。

### 對重製版的意義

這是一個**玩家看得到的功能**，不是內部機制——十組可錄可播的按鍵巨集。
規格要收，不能因為「現代玩家用不到」跳過（`CLAUDE.md` §5）。
緩衝區大小與「錄到滿就停」的行為照抄；`0xFF` 的上限是每組 255 個按鍵。

- 打字型密語的比對已經解掉，見 [`46`](46-typed-answers-and-text-input.md)。
  區塊字串表裡確實有這些明文答案（`docs/re/33` §4），
  但拿它們去比對的程式碼還沒找到；`ds:7931h` 是被多處重用的暫存區，
  `sub_139CE`／`sub_198F0`／`sub_19394` 對它的存取都是別的用途。
  **這一項不影響 §5 的結論**——不論比對來自哪裡，
  保留原文字母都是唯一同時讓鍵盤與滑鼠成立的寫法。

## 9. 這一輪學到的（寫成規則）

- **「捕捉下一個字元」這種描述要追到讀者才算解完。** 只知道寫進哪裡，
  就無法判斷中文化能不能動它——這個欄位寫了兩年也不會有人抱怨，
  因為壞掉的是滑鼠，而測試從來只用鍵盤。
- **同一個位元組同時是「顯示」與「輸入」時，翻譯就不再是純顯示層的事。**
  判斷方法是問「這個字元有沒有第二個讀者」，不是問「它看起來像不像文字」。
- **兩張表相距很遠但相鄰使用時，先各自倒出來對座標。** 熱區表（`ds:0CAEBh`）
  與熱鍵表（`ds:8DDCh`）之間唯一的連結是 `y1 ＝ 5` 這個常數，
  靠讀組語看不出來，把表倒出來就一眼對上。
