# 63：資源編號與切片索引是兩件事

日期：2026-08-15 ｜ 起因是 `docs/re/61` 的實跑：**踩上傳送格進到編號差 3 的地圖**

輸入：`wl.merged.exe` 與 `game1`／`game2`，SHA-256 見 `docs/re/01`。

---

## 1. 症狀

`docs/re/60` 的傳送記錄說「→ 地圖 35」，實跑卻進了「地圖 38」。
兩個數字都由 remake 印出來，而且**沒有任何錯誤**。

## 2. 原因

資源目錄（`docs/re/06`）列的是**所有**資源，不只地圖：

```
for id, kind := range kinds {
    switch kind & 0xC0 {
    case 0x80: file = "game1"
    case 0x40: file = "game2"
    default:   continue      // ← 目錄裡有不是 MSQ 區塊的欄位
    }
    if total[id] == 0 { continue }
    out = append(out, Resource{ID: id, ...})
}
```

被 `continue` 跳過的欄位讓 `out` 的**切片索引**落後於 `ID`。
實測：**42 個區塊裡 28 個索引 ≠ ID**，從索引 14 起開始偏移
（14→15、15→16、…），後面還會再拉開。

而遊戲裡的地圖編號一律是 **ID**：

| 來源 | 欄位 |
|---|---|
| 存檔的隊伍槽表 | `+0x0A`（目前地圖）、`+0x0D`（回程地圖） |
| 傳送記錄 | `+0x03`（目標地圖） |
| 地圖編號表 `ds:BF1Ch` | 高半部的值（建築內部 → 5／11） |

**拿索引去載入不會報錯，只會走進別的城鎮。**

## 3. 修法

`BlockByID(id)` 依 ID 找，`Block(n)` 保留給「把 42 張地圖掃一遍」這種用途。
遊戲路徑（開場載入、傳送）一律走 `BlockByID`。

⚠ **既有文件裡的「資源 N」多半是切片索引**（工具與掃描都用那個順序）。
0–13 兩者相同，所以早期的筆記沒踩到；**引用編號時要標明是哪一套**。

## 4. 為什麼單元測試抓不到

每一支測試都用同一套索引：掃地圖用索引、驗證也用索引，**自洽**。
要撞出來得把「原版資料裡的編號」餵進去——也就是踩一次傳送格。

這是 `docs/re/59` 那條規則的第二個例子：
**接不起來的是規則之間，不是規則本身。**

## 5. 可重跑的完整指令

```bash
tools/go.sh test ./internal/assets/ -run TestResourceIDIsNotSliceIndex -v
tools/go.sh run ./cmd/wl-play -script "path=29:43"   # 中途踩到傳送格會印目標地圖
```

## 6. 這一輪學到的（寫成規則）

- **「編號」要問清楚是哪一套編號。** 同一份資料可以有目錄編號、
  過濾後的索引、檔案內順序三種，而它們在前十幾筆常常一樣——
  **前綴相同的兩套編號是最難發現的錯**。
- **沒有錯誤訊息的錯最貴。** 載到別張地圖不會拋例外，
  畫面照常、玩得動，只是走進錯的地方。
  這種錯只有**拿原版資料當輸入**才會現形。
