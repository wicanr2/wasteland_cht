## 1. `sub_13AE4` 的尾巴：三條路都匯進「問方向」

```
0x13C25  A5E4h ← 編號（技能編號／物品槽位移／屬性位移）
0x13C28  A5E3h ← 種類（0 技能／1 物品／2 屬性）
0x13C2C  sub_163C4                  ; 回地圖畫面
0x13C2F  sub_125BD                  ; **問方向**（§2）；取消 → 回選單重問
0x13C3D  A5E2h ← al（方向）
0x13C40  sub_164E0                  ; 把目標格設成那個方向（§3）；CF → 重問方向
0x13C45  回傳 al ＝ 種類、dl ＝ 方向、bl ＝ 編號
```

## 2. `sub_125BD`：`Which way?`

印明文 `ds:A469h`（`Which way?`，與戰鬥逃跑同一句，`docs/re/40` §3）與
按鍵表 `ds:A45Ch`，`sub_173B0` 等按鍵回索引：**0–3 ＝ 四個方向、4 ＝ 原地**；
5–9 是方向鍵的重複項，減 5 折回 0–4。ESC 取消（SF 設）。

## 3. `sub_164E0(al ＝ 方向)`：目標格 ＝ 那個方向的一格

從視窗原點（`ds:464Eh/464Fh`）換算隊伍座標，查 `ds:AAB1h` 那張方向表
把座標挪一格（原地就是腳下），再把那一格的**記錄指標載進 `ds:46AEh`**——
`docs/re/92` §6 的三支目標判定（`sub_140DD`／`14090`／`14126`）查的
`[ds:46AEh + bl]` 就是這樣指到目標格的條件閘表。CF ＝ 目標格取不到（重問）。

## 4. 施用與收尾：方向存在 `ds:A5D9h`

`sub_13C58(al, dl, bl)` 開頭把 dl 存進 `ds:A5D9h`（全檔唯一寫入點 `0x13C5B`）。
成功那條（`0x13D16`）：

```
0x13D16  bl ← 4（記錄 +0x00 bit3 設時由 sub_142B1 依通過的條件算）
0x13D23  sub_17CFF                 ; 改寫目標格
0x13D26  CF ＝ 0 → sub_1652D(A5D9h)   ; 只捲動重畫
         CF ＝ 1 → sub_1651A(A5D9h)   ; **走一步**（完整的移動管線）
```

`sub_17CFF` 的 CF 就是「有沒有真的改寫」（`0x17D76`／`0x17D78`）：

| 改寫對第一個 byte | 動作 | CF |
|---|---|---|
| bit7 設（不改） | 什麼都不動 | 0 |
| `0xFD`（沿用上一次、回報沒改） | 寫沿用值 | 0（`0x17D45` 的 `clc`） |
| 其餘（含 `0xFE`） | 兩層寫下去 | **1** |

所以「插對鑰匙門真的變成通道 → 隊伍自己走過去」「條件沒改格子 →
只重畫」。失敗那條（`0x13D3F`）用位移 6 改寫，**同樣看 CF 決定要不要走**
（`0x13D7F` 的 `jb loc_13D30`）——失敗的改寫對也可以把人送過去，
是不是用到由資料決定。

## 7. 這一輪學到的（寫成規則）

- **「沒有這個功能」要拿玩家的操作路徑重驗一次。** 92 的偽碼是從
  `call` 圖抄的，兩支夾在中間、不改資料流形狀的呼叫就這樣漏掉了。
  玩家說「應該有方向」時，先假設是自己的筆記漏，不是玩家記錯。
- **回傳的 CF 常常就是「這件事真的發生了沒」。** `sub_17CFF` 的 CF
  同時服務「要不要走過去」與 `0xFD` 的「回報沒改」，一個旗標兩個消費端。
