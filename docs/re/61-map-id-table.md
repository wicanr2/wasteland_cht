## 1. `ds:BF1Ch` 是一張表，兩種用途

`sub_1841F` 用同一個基址讀了兩次，語意由編號的 bit7 決定：

```
0x18422  al ← ds:4655h（地圖編號）
0x18427  bit7 設（負）→ 跳過下面兩條
0x1842B  al ← [bx-40E4h]        ; ds:BF1Ch[編號]
0x1842F  ＝ 40h → dx ＝ 1800h，否則 dx ＝ 600h
0x18436  ds:46B0h ← dx          ; **記錄區標頭位置 P**

0x1843F  bit7 沒設 → 直接用
0x18445  al ← [bx-40E4h]        ; ← **同一張表，換成真正的資源編號**
0x18449  ds:4655h ← al
```

表的內容（線性 `0x28D3C`，256 bytes）：

| 索引 | 值 | 意義 |
|---|---|---|
| 0–127 | `0x40` 或 `0x20` | `0x40` → 標頭在 `0x1800`，`0x20` → `0x600` |
| 128–191 | **`5`** | 資源 5（**建築內部**） |
| 192–252 | **`11`** | 資源 11（另一組建築內部） |

**所有建築內部共用兩張地圖。** 130、132、137…191 全部指向資源 5，
差別只在目標座標——每一棟建築佔資源 5 的一小塊。
`docs/re/60` 列出來的 `(25,19)`／`(6,30)`／`(30,7)` 就是那些角落。

**nibble 11 是第二多的**，42 張地圖全部都有。它的處理確實是

## 6. 這一輪學到的（寫成規則）

- **對不上的數字要當成線索，不是雜訊。** 目標地圖編號 130 超出 42，
  第一反應是「解析錯了」；實際上那是**另一個編號空間**，
  而換算表就在讀取它的那一支函式裡。
- **同一個基址被讀兩次，語意可能不同。** `sub_1841F` 對 `ds:BF1Ch`
  讀兩次，一次當旗標、一次當對照表，分界是 bit7。
  看到「同一張表用兩次」先確認是不是同一件事。
- **統計句子會過期，而且沒有人會重算。** 「只用到 0–4、6、8–12」
  漏掉了第二多的 nibble 11。**寫下數字時把重算的指令一起寫下來**，
  下一個人才驗得動。
