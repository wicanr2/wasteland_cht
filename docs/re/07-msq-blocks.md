# 07：`GAME1`／`GAME2` 切開了 —— 42 個 MSQ 區塊

日期：2026-08-13 ｜ 輸入：`game1`（`44521eef…7841d`）、`game2`（`6de4df6d…a135c47`）、
位移表來自 `wl.unpacked.exe`（`b5eb39f0…31a0`）

用 `docs/re/06` 解出的位移表實際切開兩個資料檔（`tools/split_resources.py`）。

## 1. 結果：每一個切點都落在 magic 上

| 檔案 | 資源數 | magic |
|---|---:|---|
| `game1` | 20 | `msq0`（20/20） |
| `game2` | 22 | `msq1`（22/22） |

42 個切點全部落在 4 bytes magic 上，沒有一個例外。
位移表是從執行檔的資料段讀出來的、magic 是資料檔裡的內容，
兩邊沒有共用來源——**這是「位移表理解正確」的獨立驗證**。

`msq0`／`msq1` 與檔名 `GAME1`／`GAME2` 的編號一致：`0` 對 1、`1` 對 2。

## 2. 資源數量：三個來源互相對上

| 來源 | 表 A（`game1`） | 表 B（`game2`） |
|---|---:|---:|
| 位移表遞增且在檔案大小內的筆數 | 20 | 22 |
| 目錄裡引用到的索引 | 0–19（20 個，無重複無跳號） | 0–21（22 個，無重複無跳號） |
| 實際切出且 magic 正確的區塊 | 20 | 22 |

判定表長度時**不能只看「是否遞增」**：表 B 後面兩個值 `0x13852187`、`0x25652407`
碰巧也遞增，但遠大於 `game2` 的 172,235 bytes。加上「必須落在檔案大小內」才收斂到 22。

## 3. 目錄的 50 項

| 高 2 bits | 項數 | 意義 |
|---|---:|---|
| `0x80` | 20 | 表 A（`game1`） |
| `0x40` | 22 | 表 B（`game2`） |
| `0x00` | 8 | 見下 |

`0x00` 的八項是資源編號 14、30、37、44、45、46、47、48，
而它們的 raw byte 分別是 `0x0E`、`0x1E`、`0x25`、`0x2C`–`0x30`——
**每一項的值都等於自己的資源編號**。

低 6 bits 當索引會落在 44–48，遠超過兩張表的長度，所以它們不是有效的表索引。
合理解讀是「這個資源編號沒有對應的 MSQ 區塊」（資產在別的檔案，或根本沒用），
自我指涉只是佔位。**強證據，但還沒找到讀取端來確認**，別當已確認用。

## 6. 內容是加密或壓縮的

42 個區塊的統計形狀高度一致：**每一塊都用滿全部 256 種 byte 值**，
可列印比例約 0.37（隨機資料的期望值是 95/256 ≈ 0.371），零比例約 0.02
（隨機期望 1/256 ≈ 0.004，略高但同一數量級）。

裡面明明應該有大量英文文字，卻沒有任何可讀片段——**內容經過加密或壓縮**。

兩個檔的**最後一塊是例外**（`game1` #19、`game2` #21）：可列印比例掉到 0.30–0.31、
零比例升到 0.20–0.24。它們的處理方式可能不同，也可能只是內容性質不同（例如圖形或表格），
目前沒有證據分辨。

## 7. 訂正

`docs/re/06` §2 原本寫「資源的前 2 bytes 是長度」，理由是載入器讀完 4 bytes 之後
`mov bx, ds:46B0h` / `mov cx, [bx]` 看起來像在取長度。**這是錯的**——
那 4 bytes 是 magic，而 `ds:46B0h` 在 `sub_1841F` 開頭就被設成 `0x1800` 或 `0x600`，
是緩衝區位址而不是指向剛讀進來的 header。已在 `docs/re/06` 改正。

教訓寫成規則：**看到「讀 N bytes → 取一個 word → 當長度用」的形狀，
要先確認那個 word 真的來自剛讀進來的緩衝區**，指標變數在別處被賦值是常態。

## 8. 下一步

主線是找出**解密／解壓常式**。入口很明確：`sub_11A10`（讀本體）回來之後的處理，
以及 `sub_183B1`／`sub_1841F` 的呼叫端 `sub_184E8`／`sub_18744`／`sub_1B7FE`。

在讀出演算法之前，不要套用任何社群流傳的 MSQ 解密公式——
照 oracle 優先序，機器碼永遠贏二手說法。
