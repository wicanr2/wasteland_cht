## 1. 三個數字

`TestTranslationCoverage` 對 4,827 條非空原文各算一次 key，查目錄：

| 來源 | 有中文 | 總數 |
|---|---:|---:|
| 執行檔九張表 | 406 | 426 |
| 42 個地圖區塊 | 4,400 | 4,401 |
| **合計** | **4,806** | **4,827** |

目錄長度也是 **4,806**——**孤兒 key ＝ 0**。

孤兒 key（目錄裡有、遊戲永遠查不到）是白做的翻譯，
而它不會讓任何測試變紅：`Lookup` 查不到只是回原文。

## 2. 缺的 21 條全部是刻意不翻的

沒有中文的 21 條，逐條比對 `translations/untranslatable.tsv`——**完全吻合**：
純控制碼、空白、未用槽的解碼雜訊（`docs/re/17` §1）。原文就不是文字。

門檻因此寫成「**沒翻到的必須全部在 untranslatable 清單裡**」，
而不是「覆蓋率 ≥ 99%」：

```go
if len(missing) != 0 {
    t.Errorf("有 %d 條既沒中文也不在 untranslatable 清單裡", len(missing))
}
```

**「還沒翻」與「刻意不翻」要分得開**——用百分比當門檻的話，
覆蓋率會永遠停在 99% 而沒有人知道差的是哪一種。

`translations/must-not-translate.tsv` 的 126 筆是另一回事：
打字問答的答案（`docs/re/46` §6），比對是逐 byte 全等而輸入層是 ASCII，
翻成中文玩家永遠打不出來。那些**在目錄裡**，譯文等於原文。

## 4. 這一輪學到的（寫成規則）

- **靜音的子系統最需要門檻。** 翻譯查不到就顯示原文——遊戲照玩、
  測試全綠、玩家看到英文。沒有門檻的話，少一千條和少一條沒有差別。
- **雙向都要數。** 「有幾條沒翻」與「有幾條翻了卻用不到」是兩個方向；
  孤兒 key ＝ 0 這個數字證明 key 算法與資料完全對齊，
  比覆蓋率百分比更能說明狀態。
- **門檻要對到清單，不要對到百分比。** 百分比會被「刻意不翻」稀釋，
  而清單逼你對每一條缺口表態。
