## 1. `ds:A4E0h` 的索引 5 以上就是 opcode

`sub_12C80` 對記錄 `+0x00` 的 bit7 設的那條路是
`al &= 0x7F；bx ← al × 2；call [bx − 5B20h]`——**直接**索引 `ds:A4E0h`，
沒有上限檢查。而那張表的索引 5 起就是腳本 opcode
（`ds:A4EAh` ＝ `ds:A4E0h + 10`，`docs/re/72` §3）。

出貨資料裡有 **9 筆**這樣的記錄，`kind` 是 17／23／29／40／42／48／92：

| `ds:A4E0h[n]` | 位址 | `docs/re/34` 的 opcode |
|---:|---|---:|
| 17 | `0x1A7B6` | **12** |
| 23 | `0x1A903` | **18** |
| 29 | `0x1A98D` | **24** |
| 42 | `0x1AB7B` | **37** |
| 48 | `0x1AD14` | **43** |

五筆逐一對上 `docs/re/34` §2 的表。所以：

```
bit7 沒設 → +0x00 是 section 0x10 的索引，取出的 word 才是 opcode
bit7 設   → +0x00 & 0x7F 直接索引；< 5 是設施，**≥ 5 就是 opcode −5**
```

remake 原本把 `kind ≥ 5` 當成「不是設施」→ `EnterFacility` 回 nil →
那一格什麼都不做。現在 `NewScript` 走第二條路，`World.runScript` 跟著改。

## 2. 盤點結果

`TestFacilityCoverage`（42 張地圖、23 家設施）：

| 種類 | 家數 | 清單是空的 |
|---|---:|---:|
| 醫生 | 7 | 0 |
| 商店 | 7 | 0 |
| **訓練** | **8** | **8** |
| 存檔 | 1 | 0 |

商店家家列得出商品、醫生家家有三個價格欄位。**訓練師八家全空**。

原因：訓練師記錄裡沒有技能清單。以資源 21 的 `Library` 為例：

```
82 fd fd | 04 | 20 20 4c 69 62 72 61 72 79 20 20 20 | …
kind 2    下一步 招呼字串   +0x04 起 13 bytes ＝ 名稱
```

`+0x03` 是招呼字串編號（各家不同：04／12／16／3b／48），
`+0x04`–`+0x10` 是名稱，之後就沒有屬於這一筆的東西了。
**「這家店教什麼」不在設施記錄裡。**

`sub_1BDFF` 也不是答案——它是「角色的技能陣列（記錄 `+0x80`–`+0xBC`，
每筆 2 bytes）裡還有沒有空槽」，回 CF ＝ 1 表示**學不下了**，
與店家教什麼無關。

要解的是 `0x1BBA0`（設施 2）主迴圈裡「選一個技能」那一段
（`docs/re/52` §2 只寫到「選一個技能：`sub_1CA8D` → 基礎費用」）。

## 3. 門檻寫進測試

```go
if empty[game.FacilityShop] != 0   { t.Errorf(...) }  // 商店必須家家有貨
if empty[game.FacilityDoctor] != 0 { t.Errorf(...) }  // 醫生必須有價格
// 訓練師目前 8 家全空；接上技能來源之後這個門檻會紅，提醒更新
if empty[Trainer] != byKind[Trainer] { t.Errorf(...) }
```

第三條是**反向門檻**：現況是「全空」，一旦有一家非空就會紅——
逼下一個人回來更新這份文件，而不是讓缺口悄悄變成半好半壞。

## 5. 這一輪學到的（寫成規則）

- **跳表沒有上限檢查，就不要假設索引有上限。** `kind` 欄位看起來只有 0–4
  五種設施，實際上同一張表往後接著 44 個 opcode，資料裡真的有記錄用了
  17／23／29／42／48。**「這個欄位的合法值有幾種」要從表的長度讀，不是從語意猜。**
- **反向門檻擋得住「悄悄修好一半」。** 訓練師現在是「八家全空」——
  寫成 `!= 全部` 會在第一家接上時就紅，比寫 `== 0` 有用。
- **同一把尺量到第三個子系統。** 腳本量出 37 格、遭遇量出 0 次、
  設施量出 8 家空殼與 9 筆走錯路的記錄。**量測本身比逐個讀程式碼快得多**，
  而且每次都留下一個會擋回退的門檻。
