## 1. 結論

原版的音效是**自己寫的一台位元組碼直譯器**，跑在 `int 08h` 的計時器中斷上，
輸出到 PC 喇叭（8253 channel 2 ＋ port 61h）。

- **四個聲部**，各一份 `0x2E` bytes 的狀態結構。
- PC 喇叭一次只發得出一個音，所以四個聲部是**優先序仲裁**不是混音：
  每個 tick 掃過去，第一個「還有時值而且閘控非零」的聲部贏，**編號小的優先**。
- 每個聲部有**滑音、線性分段封套、顫音、移調**——以 1988 年的 PC 喇叭音效來說，
  這套東西相當完整。
- **九個音效**，資料全在 `seg005`（線性 `0x39200`–`0x39560`，864 bytes），
  不在任何外部檔案裡。

推論等級：**已確認**（整條鏈都讀到程式碼，資料也逐 byte 反組譯過，§5）。

## 2. 計時器

`sub_1CB75`（安裝）：

```
0x1CB7C  b80835 cd21  mov ax,3508h; int 21h    ; 取原本的 int 08h 存進 cs:dword_1CB71
0x1CB94  b80825 cd21  mov ax,2508h; int 21h    ; 掛自己的（seg001:0x00C9）
0x1CB9A  b0b6 e643    mov al,0B6h; out 43h     ; 8253 控制字：channel 2、mode 3（方波）
0x1CB9E  b8e324 e640…              out 40h ×2  ; channel 0 的除數 ← 0x24E3
```

除數 `0x24E3` ＝ 9,443 → **tick ＝ 1193182 ÷ 9443 ＝ 126.36 Hz**。

ISR（`0x1CC29`）每個 tick：

1. `call sub_1CB67`——遠呼叫，只做 `dec word_29F70`（`seg002` 裡的一個計數器）。
2. 不是重入的話（`ds:01EFh` 忙碌旗標）就 `call sub_1CC76` 更新聲部並推喇叭。
3. `dec ds:01DAh`；**每 6 個 tick 才鏈回原本的 int 08h**，其餘 tick 自己發 EOI。

所以 DOS 時鐘收到的頻率是 126.36 ÷ 6 ＝ **21.06 Hz**，比 BIOS 的 18.2 Hz 快約 15%。
**這件事對重製版沒有影響**（我們不靠 DOS 時鐘），列在這裡是因為它會讓
「在 DOSBox 裡量時間」的對拍實驗偏掉——`docs/spec/04` 的遊戲時鐘走的是自己的計數器。

推論等級：**已確認**（數值由指令直接讀出）。原版為什麼選這個除數：**未解**。

## 3. 聲部結構（`0x2E` bytes × 4，從 `seg005:0x0000` 起）

欄位名稱全部來自「哪一段程式碼讀寫這個位移」，不是從資料長相猜的。

| 位移 | 用途 | 誰在動它 |
|---|---|---|
| `+0x00` | **剩餘時值**（tick 數）；0 ＝ 這個聲部沒在發聲 | `sub_1CCC9` 每 tick `dec`，歸零就解下一批位元組碼 |
| `+0x02` | 位元組碼指標 | `sub_1CD52` 讀寫 |
| `+0x04` | 頻率除數 | 每 tick `+= [+0x06]` |
| `+0x06` | **滑音**增量（有號） | 位元組碼設定 |
| `+0x08` | 這一 tick 實際送進 8253 的除數 | `sub_1CCC9` 算完寫入、`sub_1CC76` 讀出 |
| `+0x0A` | **喇叭閘控**（`or` 進 port 61h；0 ＝ 靜音） | 封套與位元組碼 |
| `+0x0C` | 閘控增量 | 封套 |
| `+0x0E` | 音長倍率（byte；0 當 1 用） | 音符指令 `mul` |
| `+0x10` | 時值走到這個值就切封套第二段（位移設 `0x10`） | `sub_1CCC9` |
| `+0x12` | **移調**（半音） | 音符指令 |
| `+0x14` | 封套資料基底 | |
| `+0x16` | 封套目前位移（每步 +4） | |
| `+0x18` | 封套步進倒數 | |
| `+0x1A` | **顫音**波表基底 | |
| `+0x1C` | 顫音相位 | 每 tick `+= [+0x1E]` |
| `+0x1E` | 顫音相位增量 | |
| `+0x20` | 顫音深度（`imul` 的乘數） | |
| `+0x22` | 顫音相位環繞值 | |
| `+0x24` | 通用計數器 | **只有 `0xFE` 迴圈指令用**（見 §4） |

`+0x26`–`+0x2D`：**未解**（沒有任何程式碼讀寫，原版資料裡也全是 0）。

### 3.1 每個 tick 做什麼（`sub_1CCC9`）

```
時值為 0 → 什麼都不做
[+0x0A] += [+0x0C]                       ; 閘控（音量）線性變化
[+0x04] += [+0x06]                       ; 滑音
顫音：相位 += 增量；相位 ≥ 環繞值就減掉；
      (相位 >> 4) + 波表基底 → 取一個 byte 當高位元組 × 深度 → dx
[+0x08] = dx + [+0x04]                   ; 這一 tick 的除數
時值 == [+0x10] → 封套位移 ← 0x10、步進倒數 ← 1
dec 時值；歸零 → sub_1CD52（解下一批位元組碼）
dec 封套步進倒數；歸零 → 從 [+0x14]+[+0x16] 讀四個 byte：
    後兩個 byte ＝ 0xFFFF → [+0x0A] ← 前兩個（直接設閘控），位移 +4 再讀一筆
    否則             → [+0x0C] ← 前兩個（增量）、[+0x18] ← 後兩個（持續 tick 數），位移 +4
```

**封套是線性分段的**：每一段給「每 tick 加多少」與「加幾個 tick」，
`0xFFFF` 那種是「直接跳到某個值」。

### 3.2 仲裁與輸出（`sub_1CC76`）

```
四個聲部各跑一次 sub_1CCC9
再掃一次：第一個「時值 != 0 且 [+0x0A] != 0」的聲部就是它
   （四個都不符合就用最後一個）
[+0x08] → out 42h（低、高各一次）
in 61h; and 0FCh; or [+0x0A]; out 61h    ; 開／關喇叭閘
```

## 4. 位元組碼（`sub_1CD52`）

一個 byte 的 opcode，四種形狀。**指標存在聲部的 `+0x02`**，
解到「設 `+0x00`」為止算一批——時值數完才會再進來解下一批。

| opcode | 形狀 | 做什麼 |
|---|---|---|
| `0xFF` | `FF <欄位> <word>` | **設欄位**：`[聲部 + 欄位] = word`。欄位 ≠ 0 就繼續解下一個指令；**欄位 == 0（時值）就結束這一批** |
| `0xFE` | `FE <欄位> <位址>` | **迴圈**：`[聲部 + 欄位]` 為 0 → 無條件跳；否則減 1，非零才跳、歸零就往下走 |
| `0xFD` | `FD <位址>` | **換寫入基底**：之後的欄位設定套用到 `位址 + ds:018Eh`。讓一個聲部去設定另一個聲部 |
| 其餘 | `<聲部×音長> <音高>` | **音符**，見下 |

### 4.1 音符

```
高 3 位 = 目標聲部編號（× ds:01F1h ＝ 0x2E）
低 5 位 = 音長索引 → 時值 = 音長表[索引] × [聲部 +0x0E]
下一個 byte 的低 7 位 = 音高；+ [+0x12] 移調
    音高 ÷ 12 = 八度數，餘數查 12 項的半音表，除數 shr 八度數
下一個 byte 的 bit7 = 還有下一個音符（同一批餵多個聲部）
```

順手把目標聲部的封套重設（`+0x16 ← 0`、`+0x18 ← 1`）。

**一個聲部的序列可以指揮別的聲部**——高 3 位就是目標。這也是 `0xFD` 的用途。
推論等級：**已確認**（`0x1CDB2`–`0x1CE0F` 逐指令讀出）。

## 5. 資料（`seg005`）

完整反組譯在 [`generated/ida94/sfx.md`](generated/ida94/sfx.md)（`tools/summarize_sfx.py` 產生）。

| 位移 | 內容 |
|---|---|
| `0x0000`–`0x00B7` | 四個聲部的狀態（4 × `0x2E`） |
| `0x0174`–`0x018B` | **12 個半音的除數表**（最低八度） |
| `0x018C` | 目前聲部指標的暫存 |
| `0x018E` | 聲部陣列基底（`sub_1CC76` 初始化成 0） |
| `0x0190` | 音高表位址（初始化成 `0x0174`） |
| `0x0192`–`0x01D9` | **音效表**：9 筆 × 4 word ＝ 四個聲部各自的位元組碼位址 |
| `0x01DA` | 鏈回 BIOS 的分頻計數器（初值 6） |
| `0x01DB`–`0x01EE` | **音長表**（20 筆） |
| `0x01EF` | 忙碌旗標（防 ISR 重入） |
| `0x01F0` | 聲部計數器（工作用） |
| `0x01F1` | 聲部結構大小（`0x2E`） |
| `0x01F2`–` ` | **位元組碼與封套資料** |

音高表的最低八度是 **C1 ＝ 32.70 Hz**（除數 `0x8E84`）到 **B1 ＝ 61.74 Hz**。

⚠ **十二個半音裡有十一個準到 0.12 音分以內，只有 E 差了 −2.91 音分。**

| | 除數 | 頻率 | 12-TET | 差 |
|---|---|---|---|---|
| E（表） | `0x714F` ＝ 29007 | 41.1343 Hz | 41.2035 Hz | **−2.91 音分** |
| E（理論值） | `0x711E` ＝ 28958 | 41.2049 Hz | | +0.06 音分 |

差值正好是 `0x30`，而 `0x714F` 與 `0x711E` 只差第三個十六進位數字——
看起來是原始資料打錯一個字。**推論等級：強證據**（誤差形狀與其餘十一個
完全不同，而且改一個 nibble 就落回其他半音的誤差帶）。

**重製版照抄，不要修。** 走音的 E 是這台音效引擎實際發出來的聲音；
「修正」它等於改掉原版的音色。九首音效裡音效 4 用到 F 與 C，沒踩到 E，
所以這個錯在原版聽不出來——但表是共用的，重製版要留著。

⚠ **音長索引只有 0–19 落在表內。** 音符的低 5 位可以到 31，但 `0x01EF` 起
就是全域變數了。原版九個音效用到的最大索引是 14，所以碰不到——
**重製版要照樣容許 0–31，超出 20 的行為視為未定義**，不要自作主張夾住。

「長度」是實跑到自己停下來的 tick 數（`internal/audio` 的 `TestSFXLengths`）。
**靜態列表決定不了這一欄**——`0xFE` 走哪一條路要看執行期的計數器，
`tools/summarize_sfx.py` 兩條路都印得出來，但選不了。

**音效 6 是唯一停不下來的**：`0x01FA` 起兩段各 180 次的滑音擺盪跑完之後，
`0x0232` 的迴圈計數器已經歸零，`0xFE` 於是變成無條件跳，跳回 `0x01FA` 重來。
這是資料本身的形狀，不是直譯器跑掉；要停只能 `Play(0)`。

### 6.1 呼叫端是掃出來的，不是猜的

`sub_1CBD3`（播放入口）在整份映像裡**只有五個直接呼叫點**，音效編號在
前一條 `mov ax, N` 裡：

```
檔案 0x014DE  線性 0x1142E  mov ax,7
檔案 0x014EB  線性 0x1143B  mov ax,5
檔案 0x06625  線性 0x16575  mov ax,1
檔案 0x06C2C  線性 0x16B7C  mov ax,2
檔案 0x0B953  線性 0x1B8A3  mov ax,4
```

同段內的 near call 另外掃過，**零筆**。所以 0／3／6／8 在出貨的執行檔裡
沒有人播——這是全檔掃描的結論，不是「還沒找到」。

⚠ 這個掃描的射程：抓得到直接 `call far`／`call near`，**抓不到間接呼叫**
（把位址存進變數再 `call far ptr [x]`）。音效模組沒有這種跡象，但這是掃描的邊界不是證明。

**音效 4 是獨立的交叉印證**：`docs/re/31` 早就從升級的程式碼讀出「播音效 4」，
而這一輪從資料端反組譯出來的第 4 號正好是唯一一首帶旋律與封套的——
兩邊是獨立來源，這次掃描的 `0x1B8A3` 是第三份。

## 7. 對重製版的意義

- **音效資料不用另外解包**：九首全在執行檔的 `seg005` 裡，
  `tools/summarize_sfx.py` 不需要 IDA 就能倒出來。
- **不要試圖混音**。原版就是一次一個音、編號小的優先；四個聲部的意義是
  「同時排隊的序列」，不是四個同時響的音。照抄這個仲裁才會像。
- **方波要照 8253 的除數算**，不要換算成浮點頻率再合成——
  除數是整數，音準的誤差是原版音色的一部分。
- 規格見 [`docs/spec/08`](../spec/08-audio.md)。

## 8. 還沒解的

- `sub_1CB67` 遞減的 `word_29F70` 是什麼計數器。
- 聲部結構 `+0x26`–`+0x2D`：沒有任何程式碼讀寫。
- 為什麼選 `0x24E3` 這個除數（DOS 時鐘因此快 15%）。

## 10. 這一輪學到的（寫成規則）

- **「等某某先解出來」的項目要定期回頭問一次「真的還在等嗎」。**
  規格 08 掛著「等 F2 的位元組碼指令集」掛了很久，實際上直譯器只有 190 行，
  資料只有 864 bytes——擋住的不是難度，是沒人回頭看。
- **資料端與呼叫端要對得起來才算解完。** 音效 4 是從兩個獨立方向（升級的程式碼、
  資料裡唯一的旋律）撞在一起才確定的；只有其中一邊都只能算強證據。
- **表的邊界要用「下一個東西從哪開始」去定，不要用「看起來像表的長度」。**
  音長表被當成 32 筆的話，索引 20 以上會讀到全域變數——
  邊界是 `0x01EF` 那個忙碌旗標定出來的，不是表自己說的。
- **在 MZ 映像裡掃 far call，要用重定位前的段值。** 執行期的 `0x1CB6`
  在檔案裡存的是 `0x0CB6`（`0x1000` 是載入時才加上去的）。拿執行期的值去掃
  一筆都不會中，**而且和「真的沒人呼叫」長得一模一樣**。
- **函式位址推不出它屬於哪個段。** `0x1CBD3` 是 `0x1CB6:0x0073`，不是
  `0x1CBD:0x0003`；後者算出來的位移進不了機器碼，同樣是安靜的零。
  這一條是寫 `tools/scan_callers.py` 時當場踩到的——腳本裡自己推段基底，
  跑出零筆。**所以那支工具現在不接受只給線性位址。**
- **靜態反組譯決定不了「這首會不會停」。** `0xFE` 走哪一條路要看執行期的
  計數器；反組譯器兩條路都印得出來，但選不了。之前 `summarize_sfx.py` 對
  每條路的終點都寫「序列結束」，讀起來像九首都會停——實際上音效 6 不會。
  **會不會停由 `internal/audio` 實跑決定，工具只負責把路印出來。**
