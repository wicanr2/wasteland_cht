# 50：物品 70／71／72 為什麼沒有名字

95 筆物品裡有三筆沒有名字。這一份把「有哪些證據、哪些其實不算證據」分清楚，
並把能問的都問完。

## 1. 結論

| 斷言 | 等級 |
|---|---|
| 三個名字是**被清空的**，不是遺失或解碼失敗 | 已確認 |
| 三個槽的資料欄位完整（價格、類別、彈匣、骰數、彈藥都有值） | 已確認 |
| 原本的名字**開頭落在 H–M** | 強證據 |
| 物品 70 的欄位是能量武器的形狀，但類別與技能讓它不能當武器用 | 已確認 |
| 執行檔與兩個資料檔裡**問不出它們原本是什麼** | 強證據 |

## 2. 名字是被清空的，不是掉了

字串表 2 每四條一組、5-bit 打包（`docs/re/17`）。物品名 ＝ 第 `36 + 編號` 條，
所以三個槽是第 **106／107／108** 條：

```
104 'Fusion cell'        ← 第 26 組
105 'Grazer bat fetish'
106 ''
107 ''
108 ''                   ← 第 27 組
109 'Nova key'
110 'Onyx ring'
111 'Passkey'
```

兩組都**解得完整**：106／107 之後的組界對得上，108 之後三條照樣解出來。
如果是資料損毀或解碼器出錯，後面的字串會跟著錯位——**沒有**。
所以那三條在打包串流裡就是零長度：**名字被清掉，分隔還在**。

## 3. 位置把名字的開頭夾在 H–M

類別 18（劇情物品）是編號 58–90 連續 33 筆，而且**照字母排序**：

```
58 Android head   59 Antitoxin   60 Finster's head   61 Blackstar key
62 Bloodstaff     63 Bloodstaff  64 Broken toaster   65 Chemical
66 Clone fluid    67 Visa card   68 Fusion cell      69 Grazer bat fetish
70 （空）          71 （空）        72 （空）
73 Nova key       74 Onyx ring   75 Passkey          76 Plasma coupler
…
```

33 筆裡違反字母序的只有**兩筆**：60 `Finster's head`（該是 A–B）與
67 `Visa card`（該是 D–F）。三個空槽夾在 `Grazer bat fetish`（G）與
`Nova key`（N）之間，所以原本的名字開頭在 **H–M**。

⚠ 這是 **強證據不是已確認**：排序有兩個例外，而那兩個例外正好長得像
「槽被改名字沿用」。同一個現象的另一面就是這三個槽被**清掉名字**——
兩筆改名 ＋ 三筆清空，是同一種後期修改的痕跡。

`Bloodstaff` 出現兩次（62／63）也在說同一件事：**這張表本來就有沿用與重複的槽。**

## 4. 物品 70 的欄位是能量武器的形狀

| 欄位 | 物品 70 | 對照：25 `Laser pistol` |
|---|---|---|
| `+0x04` 彈匣 | 5 | 40 |
| `+0x05` 技能 | **0（沒有）** | `Energy weapon` |
| `+0x06` 骰數 | 3 | 6 |
| `+0x07` 彈藥 | `Power pack` | `Power pack` |
| 類別 | **18（劇情物品）** | 10（雷射手槍） |

彈藥指向 `Power pack`、有彈匣容量、有骰數——這是能量武器才有的組合
（全表用 `Power pack` 的只有 25–29 那五把雷射／離子武器）。
但**類別是 18、技能是 0**，所以它裝不上去也打不出去。

71／72 沒有這種特徵：彈匣 1／0、骰數 1、沒有彈藥，與其他劇情物品同形。

## 5. 兩件「看起來像證據、其實不是」的事

**庫存 0 不算證據。** 物品表 `+0x02` 是商店庫存（`docs/re/42`），
三個槽都是 0——但**類別 18 的 33 筆全部都是 0**。劇情物品本來就不擺在商店裡，
這個欄位在這裡不分辨任何東西。

**「寶箱與腳本都沒引用」也不算證據。** `tools/scan_item_refs.py` 掃了
全部 42 張地圖的寶箱格（42 個）與腳本記錄（42 筆），三個槽的引用次數是 0——
但**同樣是 0 的還有 57 個編號**，其中包括 60 `Finster's head`、61 `Blackstar key`、
73 `Nova key` 這些一定拿得到的劇情物品。

也就是說**這兩條路蓋不到劇情物品的取得途徑**（多半是 NPC 給或別的機制），
所以那個 0 不能拿來說「沒有人用」。**列出來的用意是說明它為什麼不管用**，
不是拿來當佐證。

⚠ 掃描工具自己會擋這件事：它先驗「腳本 opcode 全在 0–43、寶箱未擲定類別
全在 0–18」，任何一項超出就拒絕下結論。第一版走表走歪（把記錄 `+0x00`
直接當 opcode，其實那是 section 型別 `0x10` 的索引，`docs/re/34` §1），
opcode 分布變成 `{0, 1, 2}` 而且 op 43 一筆都找不到——**看起來就像「沒有人用」**。

## 6. 還能怎麼問下去

執行檔與兩個資料檔已經問完了：名字被清掉、資料還在、沒有可掃的引用路徑。
**要知道它們原本是什麼，只能從這份 DOS 版以外的地方找**：

| 可能的來源 | 會怎麼確認掉 |
|---|---|
| Apple II／C64／NES 版的資料檔 | 同一張表若有名字，直接填上 |
| 開發者訪談、雜誌報導 | 二手來源，只能當旁證且要標明 |

⚠ **重製版不要替它們發明名字。** `CLAUDE.md` §5 說「不要為了讓 worklist
看起來完整而發明遊戲規則」，名字同理。三個槽照原樣保留、名字留空，
翻譯目錄也不要給它們條目。

## 8. 這一輪學到的（寫成規則）

- **「沒有人用」要先證明自己分辨得出「有人用」。** 三個槽的引用次數是 0，
  但 57 個編號都是 0，其中有一定拿得到的劇情物品——**這條路蓋不到劇情物品，
  所以 0 什麼都不代表**。查詢回空之前先確認查詢對已知的正例有反應。
- **不是所有欄位都在說話。** 庫存 0 看起來像「不在遊戲裡」，但同類 33 筆全是 0。
  拿一個欄位當證據之前，先看它在同類資料裡有沒有變化。
- **空白也是資料。** 「名字被清掉」與「名字讀不出來」是兩回事，
  分辨方法是看**周圍的結構有沒有跟著壞**。壞了是解碼問題，沒壞就是原本就空。
- **排序是可以拿來推理的結構。** 一張照字母排的表，空槽的位置就把答案夾在一個
  區間裡。例外要一起數出來，例外本身往往就是同一批修改留下的痕跡。
